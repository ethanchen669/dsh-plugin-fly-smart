# 执行计划（Executing a Plan）

## 概述

计划已经思考过了。**执行它，逐步证明，留下能熬过自己遗忘的记录。**

**核心原则：The plan did the thinking; the ledger survives your forgetting.**
（计划做过思考；台账替你记住。）

**Violating the letter of this rule is violating the spirit of this rule.**

## 两种模式，同一套纪律

| 模式 | 谁实现 | 代价 | 什么时候 |
| --- | --- | --- | --- |
| **内联** | 你自己（本会话） | 只买一次上下文 + 一次终审 | 计划写得很实、任务不多、你在场 |
| **派发** | 每个任务派一个 `smart_dispatch({ role: 'hand' })` 子代理 | 每任务一个新上下文 + 一次任务评审 | 想要每任务都过评审门；或计划长到后半段会被压缩 |

**两种模式共享同一个台账与同一份格式**：中途换执行方式，新的执行者从台账接着跑。

## 铁律

```
NO EXECUTION WITHOUT A LEDGER
NO DEVIATION WITHOUT A RULING LINE
```

## 开工（每份计划一次）

1. **隔离区**：按 `smart-worktree` 建/确认工作区，**绝不在 main 上开工**（除非用户明确点头）。
2. **读计划，再读 spec**。spec 是计划论证的权威；计划内部冲突按 spec 裁。
   spec 找不到 ⇒ 台账写一行 `Spec unreachable: rulings below are provisional`。
3. **建台账**：`.dsh-fly/exec/<plan-basename>/progress.md`（git-ignored scratch），
   第一行写身份 `# exec ledger — plan: <计划文件路径>`。
   **换了计划文件就换目录**；别人的台账不读不写。
4. **预检冲突**：用计划的 `Interfaces` 块扫一遍 —— 凡是"后者消费前者的产物"，
   记一行：两个任务、谁产出什么、谁消费什么、你发现了什么。没有共享接口就写
   `Pre-flight: no shared interfaces`。每个冲突当场裁定并记在行旁，再开 Task 1。
5. 每个任务建一个 todo（todo 是活视图，台账才是记录）。

**台账是恢复地图**：它记的 commit 在 git 里真实存在，哪怕你已经不记得做过。

## 每个任务

1. **开工**：记 `BASE`（本任务从其切出的 commit），读**这个任务**的正文（不是凭记忆）。
2. **按步骤走**：计划的步骤已经是 RED-GREEN 顺序，按序执行，**看到测试失败**再写实现。
3. **每步比对 `Expected:`**，三种结果：
   - **对上了** → 下一步。
   - **代码错了** → `smart-debug` 找根因，不许改症状去凑 Expected。
   - **计划错了**（步骤与 spec 矛盾 / 上游接口对不上 / 命令不可能成立）→ **裁定**
     `Task <N>: Ruling: <发现> — <决定与理由> — <错了代价>`，继续走。
4. **提交**，按计划的提交步骤。一个任务可以多笔提交；`BASE` 是评审区间的起点，绝不是 `HEAD~1`。
5. **完成契约**（四条都成立、且有本次会话的证据，不是"看着像"）：
   - 任务点名的每个测试都存在、都在本任务里跑过、你读过输出；
   - 任务级最后一次测试运行是**绿的**（把命令与结果写进台账行）；
   - 每一条 `Expected:` 都比对过真实输出；
   - 每一处偏离都有 `Ruling:` 行。
6. **收任务**：台账追加
   `Task <N>: complete (commits <base7>..<head7>, tests: <命令> → <结果>)`。
   **血：台账行与提交在同一条消息里写** —— 压缩不挑时机，隔几条再补就是丢了。

## 裁定，不是停下（Rulings, not stalls）

一份跑着的计划不等人类。冲突、歧义、计划缺陷、想超的上限 —— **自己定**：
spec 是权威、计划是论证、你的判断补上两者都没答的。每条记
`Ruling: <决定了什么> — <为什么> — <错了代价>` 并**继续走**。
定错 = 用户看得见、能撤销的返工；停下来问 = 耗掉他一整天。

**只有四种情况停**：
1. 不可逆或破坏性操作；
2. 安全敏感动作；
3. 工作区外的副作用（合并、推共享分支、发布）；
4. 计划坏到**每条前路都是猜**。

## 压缩之后

对话记忆不熬压缩。压缩后**信台账和 `git log`，不信自己的回忆** ——
最贵的失败是执行者把已完成的整段任务重做一遍（提交明明都在）。

`.dsh-fly/exec/` 是 scratch：`git clean -fdx` 会毁掉它；真毁了就**从 git log 恢复**台账。

## 终审（整条分支，一次）

跑完最后一个任务，做**一次覆盖整条分支的终审** —— 这是这一轮唯一买到的"新眼睛"，不许省，
也不许用自己的读 diff 代替。

- **有派发能力**：`smart_dispatch({ role: 'review', prompt })`，prompt 里给：
  评审包路径（`git diff <merge-base>..HEAD` 落成文件）、计划与 spec 路径、
  计划的 `## Review Focus`（逐条检查）、台账里所有 `Ruling:` 行（让它权衡你的判断）。
  **指定模型**：终审是判断活，走 `review` 路由；回执 `source` 是 `*-fallback` 就说明
  执行模型在审自己 —— **在最终消息里告诉用户**。
- **没有派发能力**：按同一个清单自审，台账写 `Final review: self-review (no subagent)`，
  并在最终消息里说明"作者自审弱于独立评审，够不够由你判"。

**先重新定级，再动手**：评审给的严重度是建议，门是你的。按**效果**定级 ——
"一个通情达理的使用者拿到这个会怎样"，而不是"spec 有没有点名这个输入"
（spec 是愿景文档，它的沉默不是许可）。

| 级别 | 处置 |
| --- | --- |
| Critical / Important | 进**一次**修复轮：每条先写复现测试（看着它红）→ 修 → 全绿；台账记 `Final: fixed <finding> — <test> RED→GREEN, suite N/N` |
| Minor | 台账记 `Final: minor (deferred): <一句>` + 最终消息的"Deferred minors"；**不进修复轮** |
| 评审说"拒绝判断" | 每行都是你做的一条裁定，记进台账 |
| 决定不修 | 也是裁定：`Final: Ruling: <finding> — <为什么代码站得住> — <错了代价>` |

不派第二次评审：覆盖测试已经回答了"改没改"，全套已经回答了"破没破"。

## 收尾

1. 把台账里**所有** `Ruling:` 与 `minor (deferred)` 行收进最终消息
   （"我替你做的裁定"与"我选择不做的"），**穷尽、按时间序、每条带错了代价** ——
   这是它们唯一一次到达用户眼前的机会。
2. 终审干净、修复已提交 ⇒ 删掉本次计划的 workspace（git 历史就是记录），别人的目录别动。
3. 交 `smart-finish` 做集成（合并 / PR / 保留）。

## Red Flags —— 停下

- 没有台账就开了工，或台账行攒着"等会儿补"
- 压缩后凭记忆重做任务（先读台账与 `git log`）
- 计划错了就默默改成"对的"，没写 Ruling
- 每完成一个任务就问用户"要不要继续"
- 终审跳过了，或用自己的读 diff 代替
- 评审给 Minor 就照收（先按效果重新定级）
- 修复轮开了第二次

## Rationalization Prevention

| 借口 | 现实 |
| --- | --- |
| "我记得 Task N 说的是…" | 你记的是摘要。正文有精确取值，去读 |
| "测试肯定会失败，跳过看它红" | 没看着红的测试证明不了任何事。那是一步，跑它 |
| "我最后跑一次全套就行" | 逐步跑才知道是哪一步坏的；任务级那次是契约，不是替代品 |
| "计划这里不对，我直接按对的做" | 按对的做，**并且记裁定**。没记的偏离是偷偷做的决定 |
| "台账等几个任务一起补" | 压缩不挑方便的时候。一任务一行，与提交同一条消息 |
| "问一句用户更稳妥" | 他选执行是要少花时间，不是来答"要不要继续"的。只有四种情况停 |
| "我仔细读了 diff，终审多余" | 同一个作者，同一个盲区。终审是这轮唯一的新上下文 |
| "测试应该会过" | "应该"不是证据。契约要命令和输出 |

## 与其它技能的关系

- **上游**：`smart-plan` 产出计划；`smart-acceptance` 的验收件就是每步的 `Expected:`；`smart-worktree` 提供隔离区。
- **同轮**：`smart-tdd` 管每个步骤的节奏；`smart-debug` 管"代码错了"；派发与终审用 `smart_dispatch` 工具（`role: 'hand'` / `role: 'review'`）。
- **下游**：`smart-verify-claim` 管任何完成声明；`smart-finish` 管集成。
