# smart-plan — 写实现计划（计划文档契约）

## Overview（写给谁看）

**为一个没见过这个代码库、也没见过这份 spec 的工程师写。** 假设他写得了项目语言的惯用代码——只要给他精确的接口和精确的测试；计划留白的地方他会做合理选择。**他们写得了惯用代码，但不知道你决定了什么：哪些文件、哪些名字与签名、spec 里的哪些取值、哪些测试证明哪个任务** —— 把这些写下来。整个计划拆成一口一个的任务。DRY。YAGNI。TDD。频繁提交。

动手写之前先声明：「我在用 smart-plan 技能写实现计划。」

写计划用到的 DSH 工具：`bash`（跑测试与命令）、`read`（读代码库与 spec）、`write`（落盘计划）、`edit`（就地修订计划）、`grep` / `glob`（查既有模式与精确路径）。

## 落盘位置

- 本技能的产物是**一份普通 markdown**：`docs/plans/<YYYY-MM-DD-<name>.md`，本文档契约的每一节都写进去。
- 验收契约另存一份：`docs/plans/<YYYY-MM-DD-<name>>-acceptance.md`（计划与验收拆两份，互相链接）。
- 写完跑 `smart_check_doc`：plan 与 acceptance 的契约缺口会逐条列出来，补齐再交给别人。

## Scope Check（范围检查）

spec 覆盖多个独立子系统时，它本该在头脑风暴阶段被拆成子项目 spec。没拆的话，建议拆成多个计划 —— 一个子系统一份，每份计划各自产出能跑、可测的软件。

## File Structure（先定文件结构，再拆任务）

拆任务之前，先画出要新建/修改哪些文件、每个文件负责什么。分解决策在这一步定死。

- 按边界清晰、接口明确的设计单元切；一个文件一个明确职责。
- 你能一次装进上下文的代码思考得最好，文件聚焦时编辑也更可靠。宁要小而专的文件，不要什么都干的大文件。
- 一起变化的文件住在一起。按职责拆，不按技术分层拆。
- 已有代码库跟既有模式走：代码库用大文件就不要擅自重构 —— 但你要改的那个文件已经臃肿到失控时，在计划里安排一次拆分是合理的。

文件结构决定任务分解：每个任务产出能独立成立的自包含改动。

## Task Right-Sizing（任务切分判据）

**一个任务是自带测试循环、值得一个新评审者守门的最小单位。** 划任务边界时：把搭建、配置、脚手架、文档步折进需要它们的那个交付物所属的任务；**只在评审者能有意义地拒绝一个任务而批准相邻任务的地方切**。每个任务以一个可独立测试的交付物收尾。

## Step Granularity（步长判据）

**一步 = 一个可检查结果的动作。** 原文那组例子就是尺子，一格不多一格不少：

- 「写失败测试」—— 一步
- 「跑它、确认失败」—— 一步
- 「写让测试通过的最小实现」—— 一步
- 「跑测试、确认通过」—— 一步
- 「提交」—— 一步

## Plan Document Header（计划文档头部）

**每份计划必须以此头部开头：**

```markdown
# [功能名] 实现计划

> **给执行者：** 按任务逐个实现本计划，步骤用复选框（`- [ ]`）跟踪；
> 执行方式见文末 Execution Handoff。

**Goal:** [一句话：这份计划造出什么]

**Architecture:** [2–3 句：技术路线]

**Tech Stack:** [关键语言 / 库]

**Spec:** [本计划实现的 spec / 设计文档路径 —— 计划是拿着 spec 辩证的，
spec 随计划一起走，执行者两个都读]

## Global Constraints

[spec 里项目级的硬约束 —— 版本下限、依赖限制、命名与文案规则、平台要求 ——
一条一行，**逐字抄 spec 的精确值**。每个任务的需求都隐含本节。]

## Review Focus

[spec 暗示了、但没有任何任务的测试覆盖的输入类别或失败模式里，最可能咬到使用者的
**5 类** —— 一条一行，点名那个输入/条件，加上一个通情达理的人会期待的行为，
最可能的排最前。spec 是愿景文档：它说软件必须做什么，不说它会遇到什么，
**spec 的沉默不是允许程序在这个输入上坏掉**。
拿着 spec 把这张单子在这里写一次；然后给每一行补上把它钉到拥有那段代码的
任务上的测试，用那个任务自己的步骤风格写。]

---
```

## Task Structure（任务结构）

````markdown
### Task N: [组件名]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

**Interfaces:**
- Consumes: [本任务用到的前序任务产物 —— 精确签名]
- Produces: [后续任务依赖的产物 —— 精确的函数名、参数与返回类型。
  **一个实现者只看得到自己的任务，这一块是他怎么知道邻居任务
  用什么名字和类型。**]

- [ ] **Step 1: 写失败测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: 跑测试、确认失败**

Run: `pytest tests/path/test.py::test_name -v`
Expected: FAIL with "function not defined"

- [ ] **Step 3: 在 `exact/path/to/file.py` 实现 `function(input: InputType) -> ResultType`**

签名和测试之外还留有选择时（用哪个库调用、用哪种数据结构），用一行说路线；
只有它们定不了的算法才给代码块。

- [ ] **Step 4: 跑测试、确认通过**

Run: `pytest tests/path/test.py::test_name -v`
Expected: PASS

- [ ] **Step 5: 提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

**Files** 精确到路径，用 `glob` 核对既有路径真的存在。**Interfaces** 的 Consumes / Produces 都给精确签名，不许写「用上一步的输出」这种话。

## What a Step Contains（一步里放什么）

一步做到**让实现者能写出唯一合理的一个动作**即够 —— 整个要求就是无歧义，不是完备。每类步骤带上让它无歧义的那点东西，多的不放：

- **测试步**：测试名和断言，写成代码，里面是 spec 的精确取值。
- **代码步**：精确签名（名字、参数、返回类型）、它住在哪个文件、spec 钉死的取值。函数体由实现者写；体只出现在签名和测试定不了的算法、或 spec 固定的逐字文案处。
- **验证步**：用 `bash` 跑什么命令、什么输出算通过。
- **引用别的任务**：那个任务的 Interfaces 块说明用什么；计划不重复那个任务的代码。

计划 = 实现者自己定不了的那些决定的集合。两种相反的失败都要抓：

1. **什么都不决定的行**："TBD"、"handle edge cases"、"加适当的校验"、"为以上写测试"、没有任何任务定义的类型或函数 —— 空洞。
2. **已被签名和测试决定的函数体** —— 那是程序的转写稿。

## Self-Review（写完自查五条）

完整计划写完后，换双新眼睛对着 spec 把计划查一遍。这是你自己跑的清单，不是派子代理：

1. **Spec coverage**：逐节/逐条过 spec，每条都指得到实现它的任务吗？列出缺口。
2. **步长扫描**：每一步都要让实现者能写出唯一合理的一个动作，且不多于它：什么都不决定的行是缺口，签名和测试已经决定的函数体是转写稿 —— 两种都修。
3. **类型一致**：后面任务用的类型、方法签名、属性名和前面任务定义的对得上吗？Task 3 叫 `clearLayers()`、Task 7 叫 `clearFullLayers()` 就是 bug。
4. **Review Focus**：spec 暗示的每一类输入/失败模式，都有任务的测试练到吗？最可能咬人的五个没覆盖的进 Review Focus 节，每行的测试补进拥有它的任务。空节 = 查过了确实没有，不是跳过了查。
5. **Proportion**：拿计划长度和 spec 的比。**比它实现的代码还长的计划是程序的转写稿。** 代码块占了文档大半，就换成签名、测试名与断言，并确认每一步仍然无歧义。

发现就地修，修完继续，不用重查。发现 spec 需求没有任务，补任务。

## Execution Handoff（执行交接）

计划落盘并自查完，交给用户读，并定执行方式。

**还没有指定执行方式时：**

> **计划写完了，存在 `<计划路径>`。请过一遍计划。执行方式选哪个？**
>
> - **自己执行** —— 我在本会话里按计划逐任务实现，最后整体评审一遍。最快最省；中途没有独立评审。
> - **派给 hand 模型** —— 用 `smart_dispatch({ role: 'hand', prompt })` 把任务派给面板配置的 hand 路由，重要交付再用 `role: 'review'` 派一个独立评审。多一道独立视角；每次派发多一轮。
>
> **这份计划我推荐 <二者之一>，因为 <从计划里取一句：任务之间接口依赖有多重、任务有多少个、出货的错代价多大>。计划符合你的意图吗，用哪种方式？**

**已经指定执行方式时：**

> **计划写完了，存在 `<计划路径>`。请过一遍计划，符合你的意图吗？**

自己执行就按本计划的任务序号 + 复选框推进，每个任务走完 Step 的测试循环再提交；派给 hand 模型则把整个任务块交给 `smart_dispatch`，收回后用 `smart-verify-claim` 对账。

## 与其它技能的关系

上游：`smart-brainstorm`（方案）→ `smart-design`（形状）→ 本技能（步骤）；验收件由 `smart-acceptance` 先于实现写；计划每个任务的 `**Interfaces:**` 逐字抄设计的「接口」节，不许另发明一套。

## 与工具面的关系

`smart_check_doc` 在写入后校验本文档契约（Interfaces / Global Constraints / Review Focus）；`smart_dispatch({ role: 'review' })` 可以把计划派给评审路由看可行性。
