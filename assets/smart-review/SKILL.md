# 执行评审（Doing the Review）

## 概述

评审是**用证据回答"这东西会怎么坏"**，不是打分、不是鼓励、不是找格式。

**核心原则：Evidence before verdict.**（判词之前先有证据。）
**Violating the letter of this rule is violating the spirit of this rule.**（违反字面就是违反精神。）

## 铁律

```
NO FINDING WITHOUT A REPRODUCTION
NO VERDICT WITHOUT CHECKING THE THING THE AUTHOR CLAIMED
```

一条发现要么带**复现步骤**，要么带 `文件:行` + **实际读数**。
"感觉不对"、"建议再想想"、"看起来有点乱" —— 不是发现。

## 三档终态（与 smart-verify-claim 的「发现对账」同一套语言）

| 终态 | 什么算 | 必须附带 |
| --- | --- | --- |
| **阻塞** | 不改就不能合：数据丢失、错误被吞、泄漏、破坏既有调用方、安全、计划不可执行 | 复现步骤或 `文件:行` + 读数；以及"改完怎么验" |
| **非阻塞** | 建议，可以另开 PR | 为什么值得改 + 代价（改不改的取舍） |
| **需要裁决** | 问题在 spec / 需求本身（自相矛盾、与测试冲突、沉默处），不是代码 | 冲突双方原文 + 选项 + 你的推荐 |

不许第四种终态：**没写进报告**。评审报告里没出现的发现等于没发现。

## 评审什么（按对象换清单，纪律一套）

### 代码 / diff

1. **行为变化**：签名、返回类型、默认值、错误语义变了没？谁在调它（`grep` 调用方，不看就不知道）。
2. **失败路径**：错误被吞了吗（`catch {}`、`return null`、`return 0`）？调用方分得清失败与成功吗？
3. **资源**：连接、文件、定时器、监听器 —— 每条 `open` 有没有配对的 `close`/`clear`？
4. **边界**：空、0、负数、超长、重复、并发。spec **没写**的边界正是最容易坏的地方 ——
   *spec 的沉默不是允许程序在这个输入上坏掉*。
5. **测试**：新行为有测试吗？测试会在实现坏掉时红吗（问一句"把它改坏，这条测试会红吗"）？
6. **可读性以外的风格**：格式、命名偏好**不是发现**，除非它真的让人读错。

### 计划 / 产物

1. **可执行性**：另一个没见过设计对话的人，只拿这份计划能干活吗？（接口签名、文件路径、每步的验收命令）
2. **契约**：`smart_check_doc` 报的缺口就是清单（Interfaces / Global Constraints / Review Focus / 验收标准）。
3. **覆盖**：spec 的每条要求指得到任务吗？spec 暗示但没任务的输入类，写进 Review Focus 了吗？
4. **真实性**：计划里的"已实现已验"是这次跑出来的，还是抄的？（没跑过的东西出现在证据里 = 阻塞）

## 流程

1. **读作者的主张**：这份改动说它做了什么？（PR 描述、计划、提交信息）
2. **核实主张**，不是读代码找茬：他说的每一条，去代码里找对应的那一行。找不到 = 发现。
3. **按上面的清单逐项过**，每项都问"这个输入进来会怎样"。
4. **写报告**（下面的固定形状），阻塞在前。
5. **结论三态**：`通过` / `要改（列阻塞项）` / `需要裁决（列裁决项）`。
   有阻塞项或裁决项时**不许说"基本没问题"** —— 那是把判断推给读者。

## 报告形状（固定）

```
## 结论
<通过 | 要改 | 需要裁决> —— 一句话说清凭什么是这个结论

## 阻塞
1. <一句话症状> —— 复现：<步骤 / 命令 / 输入>；读数：<实际输出或 文件:行>；改完怎么验：<...>

## 非阻塞
1. <建议> —— 理由与代价

## 需要裁决
1. <冲突双方原文> —— 选项 A/B，推荐 A 因为 <...>

## 已核对
- <作者的主张> —— 核对方式与结果（"说加了重试" → 读 `saveWithRetry`，`i <= attempts` 实际是 4 次）
```

「已核对」这一节是评审的**反橡皮图章**：它证明你真的去看了作者说的东西，而不是只挑了三个格式问题。

## 派发与自审

- **重大交付走独立评审**：`smart_dispatch({ role: 'review', prompt })`，prompt 里给路径与"审什么"，
  不要给它你的结论（会污染它）。回执里的 `source` 若是 `*-fallback`，说明没有配 review 模型、
  这次是执行者的模型在审 —— **告诉用户**，别当成独立评审。
- **自审**：把 diff 当成别人提交的 PR 读，用同一份清单。你写的时候知道意图，读的时候要假装不知道。

## Red Flags —— 停下

- 你在写"整体不错，建议补充测试"这种没有具体输入的句子
- 你的发现全是格式 / 命名 / 注释
- 你说"没发现问题"却没读调用方、没看失败路径
- 作者说"已自查过"，你就跳过了核实
- 你在评审报告里写"我觉得"而不是"这里在 X 输入下会 Y"
- 有阻塞项，你却用"基本可以合"收尾

## Rationalization Prevention

| 借口 | 现实 |
| --- | --- |
| "PM 说没问题就合" | PM 没读 diff。你的判词要能自己站住 |
| "作者已经自查过了" | 自查与评审是两道不同的门。核实作者的主张是你的事 |
| "今天要发版，别挡路" | 发出去的错误比晚一天贵。阻塞项照写 |
| "只是个小改动" | 小改动也会改签名、吞错误。按清单走一遍，很快 |
| "看起来挺规范的" | 规范不等于正确。规范是格式，正确是行为 |
| "我提了三个小问题，算审过了" | 只挑格式的评审和橡皮图章一样是失败 |
| "这个边界 spec 没要求" | spec 沉默不是允许坏掉。写进非阻塞或需要裁决 |
| "review 没配就用 hand 审吧" | 那是执行者审自己。照做可以，但必须告诉用户 `source` 是 fallback |

## 与其它技能的关系

- **上游**：`smart-brainstorm` 定方案、`smart-plan` 写计划、`smart-tdd` 写实现 —— 评审是它们的下一道门。
- **下游**：评审意见由 `smart-review-receive` 处理（核实再改，不表演式同意）。
- **收尾**：评审通过后，交付方用 `smart-verify-claim` 做发现对账与四节报告。
