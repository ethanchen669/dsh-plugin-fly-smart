# 脑暴：先看再问，再摆候选

## 概述

**核心原则：You build what you believe they want, and that belief is usually thinner than it feels.**
（你造的是"你以为他要的"；那个"以为"通常比感觉上薄得多。）

**Violating the letter of this rule is violating the spirit of this rule.**

## 铁律

```
NO QUESTION THE PROJECT ALREADY ANSWERS
NO BUILDING BEFORE THE APPROACHES ARE PICKED
```

## 第一步：先看你已经知道什么

回话之前先问自己：我知道他要什么吗？为什么？

- **重要的都在请求里**（"把这个图标改成矢车菊蓝"）—— 直接做，做完说清做了什么。
- **缺了非平凡的东西** —— 开始对话。

**先看再问**：已有项目、或用户给了上下文（spec、计划、交接、点名的文件、早先的对话）——
先把那些读了、把相关代码读到能解释"今天它是怎么工作的、这次改动会碰到什么"。
**项目或上下文已经回答的问题，一个都不许问。**

## 首条消息的形状

用下面之一把工作往前推：

- **他已经说清要什么**（spec / 计划 / 详细请求）：整条消息 **约 200 字**。
  - **复述**他的请求：你要什么、给谁用、为什么（照他说到的程度）；
  - **补上你查到的**：相关的部分今天怎么工作、这次会碰到什么；
  - 如果你发现了**他没考虑到、且会改变他要求的**事（约束、冲突、更便宜的路），平实说出来；
  - 最后一句邀请他纠正。
- **他只给了模糊方向**：问**一个**问题 —— 那个答案会改变你接下来怎么做的点。
  问题要具体（"是 A 还是 B"，不是"你还想要什么"）。

后续问题**建立在答案与你的发现上**，并且**说明答案会改变什么**
（"如果选 A，我就不做缓存层了"）—— 不说明影响的问题是在闲聊。

## 摆出候选（approaches）

一旦你知道他要什么了，**把做法摆出来让他挑**：

| 列 | 放什么 |
| --- | --- |
| **问题** | 要决定的那一件事，一句话 |
| **候选** | 2–3 个真实可走的方案；每个一句代价 |
| **当前倾向** | 你推荐哪个 + 为什么 —— **这不是批准** |
| **未决问题** | 只有用户能定的那几个 |

- 候选少于 2 个 = 还没想开；候选没写代价 = 没想。**"不做"是一个候选**，只要它真实存在。
- **放在单独一条消息里**，让他挑 —— 不要混在长篇分析里。
- 「当前倾向」是倾向，不是决定：用户没点头之前，它在语义上是 **NOT approved**。

## 批准后才动工

顺序是硬的：

1. 摆候选 → 用户挑一个；
2. 写**设计文档**（形状：组件 / 接口 / 数据 / 错误 / 接缝 → 交给 `smart-design`；
   长决策要留档 → `smart-adr`）；
3. 用户批准这份设计；
4. 才进 `smart-plan` 写计划。

**什么都不建，直到设计被批准。** 上游实测：这条纪律加上之前，24/24 次运行跳过设计文档直接开写；
加上之后 3/24 —— 仍然会漏，所以它是铁律不是建议。

## 两种不算"动工"的例外

- **Spike（用户点头的探路）**：他只想摸一摸，就让路。spike 不带测试纪律、限时、代码是丢弃物 ——
  结束说清"这是 spike，不要合"。
- **用户明确说别问了**：他要的就是"按我说的做"。做了，说清做了什么。

## Size the Work（按大小定文档长度）

| 规模 | 设计文档 |
| --- | --- |
| 一句话能说清（改个值、换个图标） | 不写文档，直接做 |
| 小改动（一个函数、一个接口） | 短文档：一段 approaches + 一条接口 + 一条失败路径 |
| 新功能 / 跨模块 | 完整五问（`smart-design`） |

## Red Flags —— 停下

- 问了一个项目里已经写着答案的问题
- 首条消息超过 200 字（他说清需求时）
- 只有方案没有代价
- 把「当前倾向」写成"我决定"
- 没等批准就开始写代码 / 写计划
- 未决问题被自己悄悄拍板
- 问题连着问五个，每个都不说明答案会改变什么

## Rationalization Prevention

| 借口 | 现实 |
| --- | --- |
| "问题很简单，不用问" | 简单就直接做；但**先确认**它真的简单（看代码，不是看措辞） |
| "先写起来，边写边定" | 那是把决定埋进代码，事后没人看得见 |
| "推荐就是决定" | 倾向不是批准。用户没点头就还是未决 |
| "问用户太烦" | 问**一个**会改变方向的问题是省时间；连问五个才是烦 |
| "设计文档太重，跳过吧" | 小改动就写短的（Size the Work）。跳过不是选项 |
| "他说清楚了，我直接建" | 复述一遍（200 字），让他有机会说"不是这个意思" |
| "spike 也要按流程" | spike 是例外，但要他说 yes，而且结束后要标明"丢弃物" |

## 与其它技能的关系

- **下游**：`smart-design`（形状五问）→ `smart-adr`（取舍留档）→ `smart-plan`（步骤）。
- **平级**：`smart-acceptance` 在方案定了之后就能先写"怎么算过"。
