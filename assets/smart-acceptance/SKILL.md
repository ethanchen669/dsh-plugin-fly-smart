# 验收设计（Acceptance Design）

## 概述

**核心原则：Acceptance is written before the implementation, and it is executable.**
（验收先于实现写，而且必须可执行。）

**Violating the letter of this rule is violating the spirit of this rule.**

## 铁律

```
NO ACCEPTANCE CRITERION WITHOUT A CHECK AND AN EXPECTATION
A CHECK THAT CANNOT GO RED IS NOT A CHECK
```

## 三种验收件（fixture / gate / probe）

| 件 | 是什么 | 什么时候用 |
| --- | --- | --- |
| **fixture** | 造一个最小真实输入（文件、镜像、目录、会话），把系统推到被测状态 | 行为取决于环境形状时（配置文件长什么样、目录里有什么） |
| **gate** | 一道会红的断言：不合格就**拒绝**，不是提醒 | 判据是硬规则时（契约、格式、"必须存在/必须不存在"） |
| **probe** | 一次实测读数：跑起来、采样、比数字 | 判据是"实际行为"时（报错原文、像素、延迟、"改坏会红"） |

一条验收标准至少配一个；**能用 probe 就不用"看着对"** ——读数可以争论，感觉不能。

## 验收标准（固定形状）

```
- [ ] **A<n> <一句话标准>** —— 检查：<命令 / fixture + 断言 / probe>；预期：<可观察的结果（退出码 / 报错原文 / 读数区间）>
```

- **检查**和**预期**缺一不可（`smart_check_doc` 就查这两个词）——没有预期的检查等于没有标准。
- 预期写**可观察的读数**："exit 0"、"报错文案含 X"、"计数从 1 变 2"；不写"正常"、"合理"、"没问题"。
- 每条标准命名成**会红的那种话**："空镜像时报错并指路"，不是"镜像处理"。

## 流程

1. **先写验收，再写实现**（`smart-plan` 的任务里，Step 1 就是"写失败测试"——那条测试就是验收件）。
2. 每条需求至少一条标准；spec 沉默的输入类也要有（*spec 的沉默不是允许程序在这个输入上坏掉*）。
3. **A/B 证明检查会红**：把实现改坏（真实的失败模式，不是加注释），验收件必须红且红在正确的断言上 ——
   改坏了还绿的检查是装饰品，删掉或改到会红。
4. 覆盖不到的部分**显式说出来**：`## 覆盖说明` 一节写"哪条没有自动化验收、靠什么顶" —— 缺席要可见。
5. 落盘 `<slug>-acceptance.md`，跑 `smart_check_doc` 补齐缺口。

## Red Flags —— 停下

- 标准里只有"检查"没有"预期"，或者预期是"正常/合理/符合预期"
- 验收件从来没红过（没做过 A/B）
- 实现完了才补验收（那是给自己的实现背书，不是验收）
- 标准写成功路径、不写失败路径
- "这个没法自动化"就整条删掉（应该写进覆盖说明，不是消失）

## Rationalization Prevention

| 借口 | 现实 |
| --- | --- |
| "测试全绿就是验收" | 测试只证明它盖到的那部分；验收是"盖到哪、没盖到哪"的完整清单 |
| "先实现再补验收更快" | 实现后写的验收会绕开实现的弱点——你已经知道哪里会红了 |
| "probe 太麻烦" | 一次 probe 五到十行；"看着对"在交付后要花十倍代价 |
| "改坏了会红不用证" | 没红过的检查是装饰品。A/B 一次，省掉一整轮假绿 |
| "这条标准写不成命令" | 写进覆盖说明：靠人工看什么、什么时候看。缺席可查，消失不可查 |

## 与其它技能的关系

- **上游**：`smart-design` 的错误与失败模式是验收件的来源（每条失败路径一条 probe）。
- **平级**：`smart-tdd` 的"先写失败测试"就是本技能的 Step 1——TDD 管节奏，本技能管**标准的形状**。
- **下游**：`smart-verify-claim` 收尾时逐条跑这些验收件、做发现对账；`smart-review` 审别人时用同一份清单问"这条标准会红吗"。
