# 设计：定形状（Designing the Shape）

## 概述

**核心原则：Design is the shape, not the steps.**（设计说东西长什么样，计划说按什么步骤造。）
**Violating the letter of this rule is violating the spirit of this rule.**

## 铁律

```
NO DESIGN WITHOUT AN ERROR MODEL
NO STEPS IN A DESIGN DOCUMENT
```

设计里出现 "Step 1 / Step 2" = 写错文件了（那是 `smart-plan` 的活）；
设计里没有"失败时会怎样" = 还没设计（成功路径人人都会画）。

## 设计五问（固定形状）

| 节 | 必须回答 |
| --- | --- |
| **组件与边界** | 每个模块一句话职责；**谁不许知道谁**（依赖方向画出来）；什么不放进这个设计（裁掉的部分） |
| **接口** | 每个接缝的签名：名字、输入、输出、错误 —— 精确到"另一个人照着写不出第二版" |
| **数据与状态** | 数据长什么样、住在哪、谁拥有它、生命周期（谁创建、谁销毁、掉电/崩溃后剩什么） |
| **错误与失败模式** | 每个接口失败时会怎样：抛什么、传给谁、调用方怎么区分"失败"与"空"；网络/磁盘/并发进来会怎样 |
| **接缝与取舍** | 与既有系统的对接点（改谁、不改谁）；本设计**排除**了什么、为什么（理由记 `smart-adr`） |

五问就是设计的完成定义：缺一节，设计就是个草图。

## 流程

1. 确认方案已经定过（`smart-brainstorm` 的决策表有「当前倾向」且用户已拍板）——没定方案就去定。
2. 先写**组件与边界**（切错了，后面全错）。
3. 再写**接口**（签名是设计的骨架；计划里的 Interfaces 就是抄这一节）。
4. **数据与状态** + **错误与失败模式**成对写（每条接口配一条失败路径）。
5. **接缝与取舍**收尾；"为什么选它不选别的"写进 `smart-adr`（ADR-lite 五段）。
6. 转 `smart-plan` 拆任务；`smart_plan_check`/`smart_check_doc` 会查计划有没有抄齐接口。

## Red Flags —— 停下

- 只有框图和名词，没有一条接口签名
- 错误模型缺席，或只写"抛异常"（抛什么、给谁、怎么区分）
- 设计文档里出现实现步骤 / 排期 / 文件清单的先后顺序
- 组件职责写成动词清单（"处理、负责、调用"），而不是边界（"只知道 X，不知道 Y"）
- "到时候再说" 的部分正是设计要定的部分
- 设计和计划互相复制粘贴（两者回答不同问题：形状 vs 步骤）

## Rationalization Prevention

| 借口 | 现实 |
| --- | --- |
| "设计会在代码里自然成形" | 成形的是实现，不是设计。接口先定，实现才有对错之分 |
| "小功能不需要设计" | 小设计就五句话：一个组件、一条接口、一条失败路径。五句话不写，就是没想 |
| "ADR 就是设计" | ADR 记**为什么**这么定；设计定**形状**是什么。两份都留档，回答不同问题 |
| "先写计划再补设计" | 计划的 Interfaces 是从设计抄的；设计缺位，计划只能拍脑袋 |
| "错误处理实现时再加" | 错误模型决定接口形状（返回值还是抛错、要不要 Result）；事后加 = 改签名 |
| "画个架构图就够了" | 图说不清签名和失败路径。图是配菜，五问是主菜 |

## 与其它技能的关系

- **上游**：`smart-brainstorm` 拍板方案；方案没定就回去定。
- **平级**：`smart-adr` 记决定的理由（含错了代价 / 重开条件）；设计里"排除了什么"指向它。
- **下游**：`smart-plan` 按设计拆任务（Interfaces 逐字抄设计的接口节）；`smart-acceptance` 把「错误与失败模式」逐条变成会红的验收件；`smart-review` 把设计当对象审（五问就是评审清单）。
